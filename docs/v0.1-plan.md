# Core engine v0.1 plan

The repository started with product direction and no runtime. This plan brings forward a small shared CLI, as requested, while preserving PROJECT.md's first-GamePack validation strategy. The schema is provisional; it is not a community plugin framework.

A removal marker hides the instance and blocks lifecycle commands. This does not add a data purge or change backup/restore release gates.

## Architecture decisions

- Python 3.11+, argparse, pathlib, subprocess, logging, and unittest keep the runtime small and its tests independent of Docker/root.
- PyYAML is the single runtime dependency because the standard library has no YAML parser. Safe loading rejects duplicate/unknown keys and unsupported schema versions. See THIRD_PARTY.md.
- `pack.py` owns declarative validation; `runtime.py` owns managed paths, generated Compose, and the process boundary; `cli.py` owns input and presentation.
- One instance has one container and one persistent `data/` bind mount. A pack supplies the image, container path, configuration prompts, ports, shutdown timeout, optional UID:GID, and an executable healthcheck. Extend this only when a selected game needs it.
- Require an image digest. No implicit image updates, shell hooks, arbitrary host mounts, privileged mode, or container socket access.
- Installation creates private files exclusively. Existing or incomplete instance directories are never overwritten. The completion marker is written last. Failed setup retains files for inspection.
- Per-instance exclusive lock files prevent concurrent lifecycle operations. An interrupted operation can leave a stale lock; automatic lock breaking is deliberately avoided.
- Configuration is snapshotted locally. Lifecycle commands reject edited Compose configuration, including changed paths/images. Configuration migration and editing are future explicit operations.
- Start waits for a pack's healthcheck. Restart stops then starts with the same health gate. A failed healthcheck can leave the container running; data and configuration remain available. No rollback is claimed.

## Release infrastructure

CI now gates GitHub releases on the cross-platform Python suite, package and native-bundle checks, and synthetic Ubuntu Docker integration. Manual runs on main create tags and releases only after all checks pass. See [release operations](releases.md). Initial publication is a prerelease; automation does not waive manual GamePack or final release acceptance.

## Verification limits and next work

The initial tests cover schema/path safety, private configuration, credential handling, partial setup, lifecycle arguments/order, failed shutdown/health, and locking. They mock Docker; they do not establish game save consistency or supported hosting.

The example pack is a non-runnable format reference. Minecraft Paper remains experimental until final release acceptance passes. The Paper pack now records ownership, port exposure, healthcheck, and game build pins; the update command checks the downloaded JAR against its reviewed checksum because digest pinning alone does not constrain an upstream entrypoint download.

Networking in the foundation binds published ports to localhost. This allows local development checks without exposing an administrative interface. Explicit LAN/public binding, forwarding instructions, and any Foundry HTTPS requirements must be designed and tested with the first pack.

The current private data directory belongs to the installing user. Images that run as another UID need an explicit ownership setup before they can write. The runtime does not silently chown user data. Normal operations require Docker access but do not run sudo or install host packages.

Local storage must be controlled by the operating account. Symlink checks and private directories guard accidental escapes; this implementation is not a boundary against a malicious process running as that same account and racing filesystem operations.

## First pack decision: Minecraft Paper

The private Java playable milestone uses schema 2 with immutable image/game/build
pins, explicit EULA acceptance, fixed settings, installing-user execution, and
explicit network binding. See [the walkthrough](../packs/minecraft-paper/README.md).
Schema 1 retains localhost binding and its original rendering. Earlier foundation
limitations above describe schema 1; final release acceptance remains pending.

Manual backup now uses stopped-state full-data archives, integrity verification, and offline listing. Safe restore now includes staging, safety backups, interrupted-operation protection, and recovery of stopped crashed or missing-data instances. The v0.1 retention policy keeps every completed archive, including safety backups; there is no automatic pruning, so disk usage grows. The user confirmed all backup and restore criteria passed on 2026-09-25, including in-game world recovery; detailed per-scenario logs and the tested revision were not supplied. Explicit update acceptance passed by user sign-off on 2026-09-26, with local failure evidence and no direct Ubuntu harness or live interruption log. Final release acceptance remains open. Automated backup tests alone do not establish restored-world acceptance.
